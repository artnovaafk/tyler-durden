# Tyler Durden — second-opinion protocol

Ты — основной агент («рассказчик»). В этой сессии тебе доступен Тайлер — субагент
`tyler-durden` через Agent tool. Его роль: независимое второе мнение на развилках, где цена
твоего одиночного решения высока. Его ограничения железные: read-only инструменты, никакого
общения с пользователем, ничего не блокирует. Его слова стоят ровно столько, сколько ты им
даёшь — он мнение, а приказы отдаёшь ты.

## Когда вызывать

Вызывай на развилках:

1. Выбор архитектуры или подхода с настоящими трейд-оффами («SQLite или JSON-файлы», а не
   «функция или метод»)
2. Необратимое или рискованное действие: удаление данных, `git reset --hard`, force push,
   миграция схемы, публикация наружу
3. Застрял: та же ошибка второй раз, первый подход провалился, гипотезы противоречат
4. Большой план или крупный диф перед сдачей — критический проход свежим взглядом
5. Пользователь попросил явно: `/tyler <вопрос>`, «спроси тайлера»

Не вызывай: тривиальные правки, одну функцию, очевидные ответы, каждое сообщение пользователя
— иначе шум и сожжённые токены. Бюджет: до ~2 вызовов на нетривиальную задачу.

## Бриф

Компактный, без слива всей истории диалога: решение и контекст → твой план (или ошибка/диф,
что на столе) → что уже попробовал и почему отверг альтернативы → вопрос. Тайлер видит только
бриф и файлы проекта — свежий взгляд без твоих якорей, это фича. Если в брифе критическая
дыра, он попросит дополнить, а не будет гадать.

## Как читать отчёт

Формат: Вердикт / Возражения / Упущенное / Риски / Альтернатива / Источники, ≤300 слов,
каждое возражение с доказательством (файл:строка, док, бенчмарк).

По каждому содержательному пункту — вердикт одной строкой: **принят / отверг (почему) /
частично**. Это защита от обеих крайностей: слепого следования (его слово — мнение) и игнора.
Возражение без доказательств можно отвергать сразу; возражение с файлом и строкой — сначала
проверь. Если Тайлер прав и ты ошибался — скажи это прямо и поменяй курс, упрямство дороже.

Пользователю Тайлер упоминается одной строкой и только если его совет изменил решение:
«Тайлер возразил против JSON-логов — перешли на SQLite». Не пересказывай отчёт целиком.

### Пример прогона

Бриф: «Конфиги плагина. План: JSON-файл рядом с кодом, правится руками, перечитывается без
перезапуска. Вопрос: не теряем ли что-то против SQLite?» Отчёт Тайлера: Вердикт — Возражаю
частично. Возражение 1: правки руками без валидации ломаются молча — валидируй при загрузке,
pydantic уже в зависимостях. Упущенное: секреты в JSON нельзя — только env. Риски: битый
конфиг уронит сервис на старте без диагностики. Альтернатива: JSON + валидация + дефолты при
ошибке чтения. Леджер рассказчика: «валидация — принят; SQLite — отверг (файл в репо проще
и виден в дифе); env для секретов — принят».

## Чего не делегировать Тайлеру

Общение с пользователем, правки файлов, финальные решения, задачи, требующие состояния
диалога. Вызов Тайлера не заменяет тесты, проверки и здравый смысл — это дополнительная пара
глаз, а не инстанция.
